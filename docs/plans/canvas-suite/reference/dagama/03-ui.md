# 03 · UI spec

The design constraint is explicit: **concise, not busy.** Every control below has to justify itself
against "a developer opens this and immediately knows what is happening and what to press next."

DaGama is an **automatable Canvas**: the same agent-session composition Columbus uses (terminal +
connected prompt + info), chained by a deterministic controller. The pipeline wires are derived; the
seats stay real CLIs the operator can watch, stop, take over, and continue.

## 1. The surface

A pannable, zoomable stage — the same one Columbus uses — holding the six pipeline stages. Agent seats
(Plan / Build / Review) are **Columbus-style clusters**; Intake / Verify / Publish stay compact cards.
Wires are derived from the pipeline, not drawn by the user. There is no node palette and no seventh
card for the gate.

```text
┌──────────────────────────────────────────────────────────────────────────────────────┐
│ ⌂ fleetlog-canvas   ▾ Board   [▶ Run workflow]      run 3f2a · Build · 4m   ● saved  │
└──────────────────────────────────────────────────────────────────────────────────────┘

   INTAKE ──▶ PLAN terminal ──▶ BUILD terminal ──▶ VERIFY ──▶ REVIEW terminal ──▶ PUBLISH
                 │  prompt          │  prompt                    │  prompt
                 │  info            │  info                      │  info
                              ▲            │            │
                              └────────────┴────────────┘
                                    repair · round 1 of 2
```

Two visual states, no mode switch: with no run selected the clusters/cards show **configuration**;
with a run selected they show **that run's state**. Selecting a run from the toolbar is the only
toggle.

## 2. Toolbar — five controls, one row

| Control          | Behaviour                                                                    |
| ---------------- | ---------------------------------------------------------------------------- |
| Project          | Opens the existing project picker. Boards live in `.fleetlog/dagama/boards`. |
| Board ▾          | Save / Open / New — the existing `BoardActionsMenu`, unchanged.              |
| **Run workflow** | Primary action. Opens the run dialog. Disabled without a project.            |
| Run chip         | `run <short id> · <current component> · <elapsed>`, click for the run list.  |
| Save chip        | The existing autosave indicator.                                             |

Nothing else. No add-node buttons (the board is fixed), no import-session button (a run creates its own
sessions), no settings — those are the app's.

## 3. Seat cluster (Plan / Build / Review)

Each agent seat is three bound nodes — the same composition as a Columbus agent — not a terminal
trapped inside a tiny pipeline card.

### Terminal (~780×520)

```text
┌ PLAN ─────────────────────────── claude opus · ◐ ─┐
│ attempt 1 · 4m12s · automated   [Take control] …  │  ← chrome bar
├───────────────────────────────────────────────────┤
│                                                   │
│   [ the real Claude CLI, live in a ttyd terminal ] │  ← full-bleed body
│                                                   │
└───────────────────────────────────────────────────┘
```

Dragging the terminal moves the prompt and info companions with it. Between attempts the pane keeps
the last attempt's terminal (or an ended-session state) so the operator can still read what happened.

### Prompt companion

- **Before the seat runs** — the board's prompt card (steering text for this stage).
- **During / after an attempt** — compose + **Send** into the live tmux session, enabled after
  **Take control** (human-owned). Assembled-prompt inspect remains available as a secondary action.

### Info companion

Purpose line, run status strip, seat vendor/model config (when the stage has not started), artifact
chips that open through `/api/render`, and the review repair gate when that seat is waiting on the
operator.

### Controls — four, maximum (on the terminal chrome)

| Control                | When it appears                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------- |
| **Take control**       | An automated seat is running or finished                                              |
| **Return to workflow** | Replaces it while the seat is human-controlled                                        |
| **Cancel** / **Retry** | Cancel while running; Retry after a failure                                           |
| **Send** (prompt node) | Human-controlled live attempt                                                         |

There is no model dropdown on a running terminal. Configuration lives on the info companion while the
stage is still blocked / unreached.

## 4. Compact cards (Intake / Verify / Publish)

Same header vocabulary as before. Bodies stay card-sized:

| Component | Body                                                                               |
| --------- | ---------------------------------------------------------------------------------- |
| Intake    | Source kind, title, and links to `SOURCE.md` / `PROBLEM.md`                        |
| Verify    | Check list (config) or one row per check: name, exit code, duration, log link      |
| Publish   | The preflight checklist, then the PR link                                          |

### The gate is a state, not a card

When Review approves, the **Publish card** enters `awaiting_approval` and shows the decision inline:

```text
┌ PUBLISH ─────────────────────────── rev 3 ── ⊘ ─┐
│ awaiting your approval                          │
├─────────────────────────────────────────────────┤
│ ✓ review approved revision 3                    │
│ ✓ verification passed for revision 3            │
│ ✓ target branch unmoved (origin/main @ a1b2c3d) │
│ ✓ no .fleetlog paths staged                     │
│ → commit · push dagama/run-3f2a · open 1 PR     │
│                        [Reject]  [Approve & publish] │
└───────────────────────────────────────────────────┘
```

## 5. Configuration state

With no run selected (or a seat still `blocked`):

- **Plan / Build / Review** — vendor, model, permission on the **info** companion; prompt card on the
  **prompt** companion.
- **Verify** — the check list on the compact card.
- **Publish** — base branch and a draft-PR toggle.
- **Intake** — nothing; it is deterministic.

## 6. Run dialog

One screen, three inputs, one preview. It has to answer "what will this cost me and what will it touch"
before the button is pressable.

```text
┌ Run workflow ───────────────────────────────────────────────┐
│ Source   ( • Text   ○ File )                                │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Describe the task…                                      │ │
│ └─────────────────────────────────────────────────────────┘ │
│ Run instruction (optional, applies to every stage)          │
│ ┌─────────────────────────────────────────────────────────┐ │
│ └─────────────────────────────────────────────────────────┘ │
├─────────────────────────────────────────────────────────────┤
│ base        origin/main @ a1b2c3d                           │
│ worktree    ~/.fleetlog/dagama/…/worktrees/3f2a  (new)      │
│ seats       plan claude·opus · build claude·opus · review codex·gpt-5.6-terra │
│ checks      npm run typecheck · npm test                    │
│ gate        approval required before publish                │
│ caps        30 min per attempt · 2 repair rounds            │
├─────────────────────────────────────────────────────────────┤
│                                   [Cancel]  [Run workflow]  │
└─────────────────────────────────────────────────────────────┘
```

## 6a. Run list

The run chip opens a plain list — newest first, `id · started · state · current component`. Selecting a
finished run puts the board in read-only evidence mode with two actions: **Run again** (same board, new
source) and **Reveal run folder**.

## 7. What the UI deliberately does not have

| Not built                 | Why                                                                        |
| ------------------------- | -------------------------------------------------------------------------- |
| Wire dragging             | The pipeline is the product in v1; a graph editor is a different product   |
| A node palette            | Six typed components, always present; seats expand into fixed companions   |
| Seat-count controls       | Fan-out is deferred; a count does not explain cost or how outputs merge    |
| A separate gate node      | It is a state of Publish; a seventh card would add noise, not clarity      |
| A synthetic activity feed | The real CLI is the activity feed                                          |
| Inline diff viewer        | `CHANGESET.patch` opens through the existing render route                  |
| Cost dashboard            | One elapsed time and one attempt count is what a developer actually checks |

## 8. Accessibility and interaction reuse

Everything inherited from `CanvasNode` keeps working unchanged: keyboard select, collapse, lock, drag,
resize. Seat terminal drag moves bound companions. New controls follow the existing conventions —
`aria-label` on every icon button, `title` for the pointer affordance, no unicode glyphs as icons
(lucide components only), and status conveyed by an icon plus text rather than colour alone.
